# Переход существующей MongoDB Calm на авторизацию

Рабочая MongoDB сейчас доступна только через `127.0.0.1`, но не проверяет учётные записи. Тест перехода с существующим отдельным томом запускается так:

```sh
bash backend/scripts/run-shared-risk-migration-test.sh
```

Тест создаёт синтетические данные, четыре учётные записи, пересоздаёт временный MongoDB с `--auth`, проверяет права приложения и экспорта и собирает настоящий Spring Boot backend. Через API он регистрирует тестовый аккаунт, добавляет ему записи риска и согласие, проверяет появление 301-го обучающего дня, удаляет аккаунт через `DELETE /api/users/me` и пересобирает выборку до 300 дней. Проверяются удаление исходных записей и строки в обучающей базе. Затем тест удаляет только свои контейнеры и том. Рабочие данные он не читает.

## Условия перед переключением рабочей базы

1. Назначить окно обслуживания и остановить запись через backend и фоновые задачи. Снять защищённую резервную копию MongoDB `calm` и тома аватаров в выбранное хранилище с шифрованием и ограниченным доступом; не оставлять незашифрованный дамп в репозитории, рабочем каталоге или Docker volume. Записать контрольную сумму и версию MongoDB/инструментов для проверки целостности и воспроизводимого восстановления. Восстановить копию в отдельной закрытой среде и проверить содержимое, индексы и запуск приложения. Синтетический тест восстановления не заменяет эту проверку. Перед пилотом также нужно настроить выбранный ниже срок хранения и проверить восстановление именно из выбранного защищённого хранилища.
2. Подготовить четыре **разных случайных пароля не короче 32 байт** вне репозитория: `CALM_MONGO_ROOT_PASSWORD`, `CALM_MONGO_APP_PASSWORD`, `CALM_MONGO_EXPORT_PASSWORD`, `CALM_MONGO_TRAINING_PASSWORD`. Если пароль входит в URI, его нужно экранировать по правилам URI. Отдельно задать `CALM_MONGO_URI=mongodb://calm_app:<пароль>@mongo:27017/calm?authSource=admin` для backend. Не выводить пароли в логи или changelog.
3. Пока текущая MongoDB работает без `--auth`, выполнить `prepare-shared-risk-mongo-users.js` через `mongosh admin --file /dev/stdin` с `CALM_MONGO_SETUP_CONFIRM=YES` и четырьмя переменными паролей. Скрипт создаёт `calm_risk_admin` (`root`), `calm_app` (`readWrite` только `calm`), `calm_risk_export_reader` (`read` только `calm`) и `calm_risk_training_writer` (`readWrite` только `calm_risk_training`). Он останавливается при совпадении паролей, слишком коротком пароле или уже существующем пользователе с одним из этих имён; после частичного сбоя сначала нужно проверить фактическое состояние пользователей.
4. После проверки созданных пользователей переключить Compose на `docker-compose.auth.yml` и передать `CALM_MONGO_URI`. Этот override запускает `mongod --auth` и не позволяет стартовать backend без URI. Пересоздать MongoDB **без удаления тома**, затем поднять backend и frontend и проверить `GET /api/actuator/health`, вход и операции с дневником. Проверить вход под `calm_risk_admin` и запреты чтения/записи для ограниченных пользователей.
5. Экспорт запускать только после утверждения условий участия, через отдельный URI записи в `calm_risk_training` и исходную учётную запись только для чтения. Не передавать приложению root-доступ или доступ к обучающей базе. Для пилота отдельно включить и наблюдать `docker-compose.training-worker.yml`; без этого отозванные данные останутся в последней опубликованной выборке до ручной пересборки.

### Проверочный лист рабочего backup перед пунктом 3

Для первой локальной копии по выбору пользователя доступен `bash backend/scripts/backup-calm-local.sh "$HOME/CalmBackups"`. Скрипт кратко останавливает backend, сохраняет `calm.archive` и `avatars.tar`, восстанавливает базу во временной MongoDB, сравнивает состав, количество, индексы и хеши коллекций, проверяет чтение архива аватаров и SHA-256, затем удаляет временный контур и снова запускает backend. Файлы имеют права только владельца. Копия в `~/CalmBackups` остаётся **незашифрованной на том же Mac**; этот вариант не выполняет условие независимого защищённого backup для перехода на `--auth` и внешнего пилота. Скрипт не удаляет старые копии автоматически.

В базовом `docker-compose.yml` данные MongoDB находятся в `mongo_data`, аватары — в `avatars_data`. Для текущего локального Compose-проекта проверены тома `calm-project_mongo_data` и `calm-project_avatars_data`; при переносе приложения или смене имени проекта их нужно определить заново. Не подставлять старые имена без проверки.

1. Записать место зашифрованного хранилища вне сервера приложения и Docker volumes, кто имеет доступ, способ восстановления ключа и срок хранения. Проверить свободное место и доступность **до** окна обслуживания. В журнал не записывать ключи, URI с паролями и пользовательские данные.
2. В окно обслуживания остановить backend и все процессы записи, включая worker, если он когда-либо будет включён. MongoDB оставить доступной для `mongodump`. Зафиксировать время начала и версии образа MongoDB и Database Tools.
3. Снять логическую копию базы `calm` через `mongodump` и архив тома `avatars_data` при остановленной записи. Передавать оба архива в выбранное зашифрованное хранилище без постоянного незашифрованного файла на сервере; записать контрольные суммы сохранённых артефактов и способ их проверки. Убедиться, что копия аватаров действительно содержит файлы, на которые ссылаются записи пользователей.
4. Из **сохранённых артефактов** восстановить MongoDB и аватары в отдельной закрытой среде без доступа пользователей и без отправки уведомлений. Сверить контрольные суммы, перечень коллекций, количество документов и индексы; выборочно проверить связанные записи и файлы аватаров. Запустить приложение на восстановленной копии и проверить вход, чтение дневника и работу API. Синтетический сценарий не заменяет эту проверку.
5. Зафиксировать результат восстановления, время, место копии, ответственного и срок удаления. Если проверка не прошла, не переходить к созданию рабочих пользователей MongoDB и `--auth`. При восстановлении старой копии для работы выполнить сброс согласий и очистку обучающих артефактов по `README-shared-risk-training.md` до открытия доступа.

Пока место хранения и ключи не определены, рабочую копию и миграцию не запускать. Подробные команды копирования зависят от выбранного хранилища и фактического рабочего хоста; их нужно проверить на нём до окна обслуживания.

Для пилота на личном Mac выбран начальный срок хранения **30 дней** для всех рабочих копий, включая ручные копии перед изменениями: снимать копию после дней использования приложения и перед рискованным изменением, удалять копии старше 30 дней из каждого места хранения. Если приложение не запускалось, последняя копия может устареть — перед следующим изменением снять новую и проверить её. Раз в месяц выполнять пробное восстановление в закрытую среду. Это проектное решение для ограниченного пилота, а не установленный законом срок; его нужно отразить в окончательных условиях участия и пересмотреть при изменении порядка обработки данных.

Предпочтительная схема — две независимые копии: зашифрованный внешний диск и удалённое хранилище с шифрованием на Mac до отправки. Один внешний диск подходит для первой проверки восстановления, но остаётся уязвимым к потере самого компьютера и диска в одном месте. Time Machine может защищать файлы Mac дополнительно, но не заменяет проверяемую логическую копию `calm` и отдельную копию `avatars_data` из Docker volumes. Перед покупкой диска или выбором облачного тарифа измерить фактический размер базы и аватаров. Способ шифрования, место хранения и удаление старых версий в облаке ещё не настроены.

Команды переключения после выполнения пунктов 1–2 и экспорта переменных в оболочку:

```sh
docker compose stop frontend backend
docker compose exec -T \
  -e CALM_MONGO_SETUP_CONFIRM=YES \
  -e CALM_MONGO_ROOT_PASSWORD -e CALM_MONGO_APP_PASSWORD \
  -e CALM_MONGO_EXPORT_PASSWORD -e CALM_MONGO_TRAINING_PASSWORD \
  mongo mongosh --quiet admin --file /dev/stdin \
  < backend/scripts/prepare-shared-risk-mongo-users.js

docker compose -f docker-compose.yml -f docker-compose.auth.yml up -d --no-deps mongo
docker compose -f docker-compose.yml -f docker-compose.auth.yml up -d backend frontend
curl --silent --show-error http://localhost:8080/api/actuator/health
```

Последняя команда подтверждает лишь здоровье API. Отдельно проверьте вход и чтение/запись дневника: health endpoint сам по себе не доказывает, что backend подключился к MongoDB с нужными правами.

Рабочее переключение ещё **не выполнено**. Не включать `--auth` до проверки реального восстановления и готовности откатить изменение. Откат подключения выполняется с остановленным backend: вернуть базовый `docker-compose.yml` для MongoDB и backend, сохранив том; созданные пользователи останутся, но авторизация снова будет выключена, пока не выполнен повторный переход. Такой откат возвращает доступность, но не заменяет разбор причины сбоя и защиту данных.

Набор участников требует одновременно `CALM_RISK_PILOT_ENROLLMENT_OPEN=true`, `CALM_RISK_PILOT_APPROVED_CONSENT_VERSION` и `CALM_RISK_PILOT_APPROVED_CONSENT_DIGEST`, точно совпадающие с текущими значениями текста на сервере; по умолчанию он закрыт. После миграции MongoDB набор должен остаться закрытым до утверждения окончательной версии текста согласия, защищённого доступа к сайту, резервных копий и наблюдаемой пересборки обучающей базы. При изменении версии или текста соответствующая настройка утверждения не совпадёт автоматически, оставляя набор закрытым.

Интеграционный тест с отдельным worker показывает автоматическое удаление строки из новой выборки после `DELETE /api/users/me`; между удалением и успешной пересборкой старая строка ещё может находиться в базе. Период запуска worker — 5 минут, но при аварии он не даёт жёсткой гарантии времени физического удаления. Перед включением реального экспорта нужны мониторинг, порядок реакции на сбой и честный срок в условиях участия.

При восстановлении старого бэкапа до открытия приложения обязательно выполнить сброс согласий и очистку обучающих артефактов, описанные в [README-shared-risk-training.md](README-shared-risk-training.md). Старый бэкап может содержать согласие, отозванное после его создания.
