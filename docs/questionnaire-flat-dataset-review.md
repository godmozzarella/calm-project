Предложение ниже реализовано отдельным протоколом v5 после опроса: [реализация и ограничения](daily-questionnaire-v5.md). Сбор v4 остаётся отдельным полуночным протоколом; смешивать эти примеры нельзя.

## 1. Сон при утреннем прогнозе

Если пользователь утром уже проснулся и прошёл опрос, продолжительность прошедшей ночи и субъективное качество сна известны до прогноза. Их можно использовать как признаки. Это делает их временно корректными, но не гарантирует существенного улучшения LR/XGBoost: пользу надо проверить на будущих наблюдениях.

Утром нельзя честно прогнозировать уже прошедшую часть дня. Пример:

- 4 ноября в 08:20 пользователь сообщает о сне и новых началах за 3 ноября.
- Ответ о 3 ноября уточняет исход за прошлый день; он не является таргетом для выдаваемого сейчас прогноза.
- Для прогноза 4 ноября сохраняются входы и `issuedAt=08:20`.
- Новый таргет — начало отдельного приступа **после 08:20 и до конца 4 ноября**.
- На следующем опросе или при позднем вводе записи выясняется фактический исход этого интервала.

Если приступ 4 ноября начался в 06:00, он уже известен к прогнозу 08:20 и не может считаться его предсказанным будущим событием. Если отдельный новый эпизод начался в 15:00 — это положительный исход данного прогноза. Продолжение ранее начавшегося приступа не является новым началом.

Следовательно, необходимы `issued_at`, `target_start_at`, `target_end_at`, timezone, локальное время выдачи и длина оставшегося горизонта. Прогноз в 08:00 и в 18:00 не имеет одинакового горизонта. Для первой модели можно ограничить анализ заранее установленным утренним окном; поздние опросы и их прогнозы учитывать явно, а не выдавать их за утренние. При неизвестном времени начала события календарный исход может быть известен, а исход утреннего интервала — неизвестен.

Это частный случай запрета использовать при обучении сведения, которых не было бы при реальной выдаче: [официальное объяснение утечки данных](https://scikit-learn.org/stable/common_pitfalls.html).

## 2. Разбор всех 23 столбцов

В таблице ниже D — день выдачи после утреннего опроса; история ограничена сведениями, поступившими к фактическому `issued_at`. Даты и ID служат ключами/группировкой, а не автоматически подаются числовыми признаками.

| Поле примера | Решение и точный смысл |
|---|---|
| `user_id` | В исследовательском файле — `participant_key` с HMAC. Использовать для связи истории и разделения выборки; не давать модели порядковый ID пользователя как число |
| `date` | Локальная дата D; дополнить временем выдачи, целевыми границами и timezone |
| `gender` | Зафиксировать, что именно собирается. Для заявленного поля пола назвать `sex` и документировать категории, включая неизвестно/не указан. Не считать его достаточным переключателем опроса о цикле |
| `age` | Возраст или возрастная группа из необязательного разового профиля. Не спрашивать ежедневно; дата рождения не обязательна для этого признака |
| `cycle_day` | День цикла, вычисленный только из уже известного начала. Нерегулярность/нет сведений/не применимо/отказ не превращать в 0. Не фиксировать всем цикл длиной 28 дней |
| `weekday` | Автоматически из локальной даты D. В примере соответствует Monday=0; кодировку сохранить в словаре |
| `pressure_mmhg_fc` | Прогнозное давление из выпуска, доступного до выдачи; единицы мм рт. ст. |
| `pressure_delta_24h_fc` | Однозначно определить сравниваемые периоды и выпуски. Это известный при выдаче прогноз изменения, а не фактический перепад, полученный вечером |
| `humidity_delta_24h_fc` | Аналогично; единицы — процентные пункты, а не проценты относительного изменения. Добавить абсолютную `humidity_fc`, уже доступную в Calm |
| `temp_delta_24h_fc` | Зафиксировать, изменение какой температуры используется. Сейчас есть min/max; их полусумма не должна молча называться средней температурой. Сохранить также доступные `temp_min_fc` и `temp_max_fc` |
| `kp_index_fc` | Сохранять выпуск/время и тип значения. В коде NOAA есть прогнозный endpoint, но агрегирование сейчас не сохраняет различие observed/predicted и использует UTC-сутки. Для локального горизонта это нужно явно уточнить. В примере есть 9.4 — за пределами шкалы 0–9 |
| `sleep_hours_actual` | Сейчас смысл конфликтует с `sleep_prev_night`. Не подавать реальный сон будущей относительно выдачи ночи. При переопределении на прошедшую ночь назвать `sleep_hours_last_night`, оставить один такой признак |
| `sleep_prev_night` | В примере это точный лаг `sleep_hours_actual` предыдущей строки: 35 700 из 35 700 сравнимых переходов. Для живого приложения проще хранить явно датированную прошедшую ночь, а не два неоднозначных названия |
| `sleep_est_7d` | Если это личная средняя, назвать `sleep_mean_previous_7_nights`. Считать только из предшествующих ночей, не из полного пользовательского ряда, и сохранять число известных ночей |
| `sleep_dev` | Явная формула: сон прошедшей ночи минус средний сон предыдущих семи известных/календарных ночей по выбранному правилу. Эти два варианта среднего нужно различить. При недостаточной истории — null или пометка неполного окна, не выдуманная норма |
| `days_since_attack_start` | Давность последнего отдельного начала, известного к выдаче. Если начало было сегодня до опроса, допустим 0; при отсутствии истории — null, не произвольные 60 |
| `attack_streak` | Уточнить: последовательность дней с болью или с новыми началами? Предлагается `headache_days_streak_before_issue` как прошлый клинический признак. Это не мотивационный стрик опросов. В примере положительность этого столбца совпадает с таргетом предыдущей строки, поэтому нельзя объявлять его прямой копией текущего таргета |
| `attacks_last_7d` | Лучше `episode_starts_last_7d`: число отдельных начал в определённом прошлом окне. Не смешивать число записей, дат начала и дней с болью |
| `attacks_last_30d` | То же для 30 дней; рядом нужно число наблюдаемых/подтверждённых дней, чтобы 0 в полном дневнике отличался от отсутствия данных |
| `days_no_med_streak` | Допустимо только по явно подтверждённым дням без приёма. Отсутствие записи лекарства не доказывает отсутствие приёма; при разрыве наблюдения значение неизвестно |
| `med_streak` | Последовательность подтверждённых дней приёма до выдачи. Назначение/класс и время приёма полезнее неопределённого общего счётчика; окончательные сегодняшние приёмы после выдачи недоступны |
| `med_days_last_30d` | Число дней с известным приёмом в прошлом окне; добавить полноту наблюдения и по возможности разделение классов/назначения |
| `attack_target` | Оставить бинарным или null, но определить как новое начало внутри конкретного будущего интервала. Само имя не объясняет, означает ли 1 новое начало или продолжающуюся боль |

Столбцы разумны как начальная форма, но одному имени недостаточно для доказательства допустимости признака. В отсутствие генератора/словаря нельзя подтвердить формулы всех окон и то, что генератор таргета использовал только допустимые входы. Синтетические связи не являются медицинскими закономерностями.

Для Kp границы шкалы подтверждены [NOAA](https://www.spaceweather.gov/products/planetary-k-index). Это проверка формата внешнего показателя, не доказательство его полезности для головной боли.

## 3. Что добавить к плоской таблице

### Полезные пользовательские сведения

- `sleep_quality_last_night`, например согласованная шкала 1–5. Это субъективная оценка; продолжительность сна не заменяет её.
- `stress_now` или `stress_yesterday` — отдельные вопросы с разными временными периодами, их не объединять под общим «стресс». Вопрос о вчерашнем стрессе можно использовать после сегодняшнего ответа как исторический признак.
- Подтверждение лекарств за вчера: были/не было/не помню. По ответу «были» показать или предложить добавить приёмы; не требовать повторного ручного ввода уже записанного.
- Известный текущий продолжающийся приступ, текущее состояние боли и новые начала сегодня до выдачи — факты, а не предсказанный исход.
- Для цикла — включён ли учёт, применимость, доступность информации и дата известного начала. Сведения о цикле и поле должны оставаться добровольными.

### Технические поля, которые пользователь не заполняет

`questionnaire_id`, `questionnaire_version`, `completed_at`, `report_for_date`, `sleep_start_date`/`sleep_end_date` или идентификатор ночи, timezone, `issued_at`, `target_start_at`, `target_end_at`, `protocol_version`, `feature_schema_version`, `label_source`, `label_revision`, `label_available_at`, `missing_flags`, покрытие истории и происхождение выпуска погоды.

Это можно хранить как служебные столбцы и не включать всё в X. Идентификаторы, происхождение метки и будущие редакции исхода используются для контроля и разбиения, а не как подсказки о таргете. Одной строки `date` недостаточно для честного утреннего обучения.

## 4. Предложение утреннего опроса

На экране должны быть видны периоды вопросов, без необходимости разбираться в структуре модели.

1. **«Вчера начинался новый приступ?»** Да / Нет / Не помню. Если уже есть записанные начала, показать их и предложить проверить, что внесены все. Продолжение старого приступа не требует ответа «да».
2. При ответе «да» без записи — предложить добавить приступ и его время. Это нужно в том числе для проверки вчерашнего утреннего прогноза. Не заполнять неизвестное время выдуманным значением.
3. **«Сколько вы спали прошедшей ночью?»** Часы/минуты, возможность не отвечать. Ночь однозначно привязана к сегодняшнему пробуждению.
4. **«Как оцениваете качество этого сна?»** Короткая шкала.
5. **«Какой стресс был вчера?»** Короткая одинаковая шкала с возможностью не помнить. Если нужен именно текущий стресс — спрашивать его отдельно и не приписывать ответ вчерашнему дню.
6. **«Вчера принимали препараты?»** Да / Нет / Не помню, с уже записанными приёмами для проверки. Без этого нельзя честно вычислить длительную серию без лекарств.
7. Блок цикла — только по выбору пользователя; по возможности автоматически показывать ранее известную информацию и спрашивать об изменениях, а не заставлять вводить день цикла вручную каждый день.

После отправки сохраняется неизменяемый срез входов для нового прогноза. Редактирование ответов позднее меняет актуальную историю и нужные метки, но не подменяет прошлые входы. Повторную выдачу после редактирования, если она понадобится, хранить как отдельный прогноз с новым временем и горизонтом.

Перенос нынешней отдельной галочки в опрос логичен: вопрос «нет новых начал вчера» заменяет её роль для соответствующей даты. Наличие записи о приступе уже может дать положительный исход; отсутствие опроса не должно стирать известный приступ. На время разработки не удалять действующий элемент без готовой замены и соответствующего изменения API.

## 5. Профиль и цикл

Пол и возраст спрашиваются один раз при первичном заполнении профиля, с возможностью изменить или не указывать. Это не дополнительный экран при каждом входе.

Для включения чувствительного блока лучше прямой выбор **«Хотите учитывать менструальный цикл?»** с вариантами «Да», «Нет/не актуально», «Не хочу указывать». Одно поле пола не сообщает применимость и регулярность цикла. В примере цикл уже отсутствует у части условных пользователей одной категории пола — такую возможность необходимо сохранить.

Необязательный блок не влияет на завершённость общего опроса и стрик. Изменение состава исследовательских сведений нужно отразить в описании добровольного участия до production-сбора; пользоваться дневником и проходить общие вопросы можно без передачи данных в общую модель.

## 6. Стрик за заполнение, а не за отсутствие боли

Рекомендуется привязать мотивационный стрик к отправке **текущего ежедневного опроса**, независимо от того, были ли приступы. Тогда человек получает поддержку за ведение дневника, а не стимул отрицать боль.

- Учитывать фактический местный день отправки текущего опроса. `completed_at` и `report_for_date` различаются: сегодня отвечаем о вчера и прошедшей ночи.
- Один текущий опрос даёт максимум один шаг стрика; его редактирование не даёт ещё один шаг.
- Позднее изменение/добавление приступа не отнимает шаг: опрос уже был пройден.
- Массовое заполнение прошлых дней не превращается в ежедневные посещения и не восстанавливает задним числом недели стрика. Правило допуска на позднюю отправку, если оно нужно продукту, определить отдельно.
- «Не помню» и отказ от необязательного вопроса — допустимые ответы, а не повод заставлять выбирать ложное «нет» ради стрика. При этом соответствующий таргет/признак остаётся неизвестным.
- `questionnaire_streak` не заменяет клинический `attack_streak` из CSV. Использование мотивационной серии как признака модели не предполагается по умолчанию: она отражает вовлечённость и требует отдельной проверки.

## 7. Ответ «не было», затем поздняя запись приступа

Сохранить отдельно **сырой ответ опроса** и **актуальный разрешённый исход дня/прогнозного интервала**.

Пример: 5 ноября утром пользователь ответил «4 ноября новых приступов не было». Позже он добавил начало за 4 ноября в 15:00.

1. Запись приступа сохраняется как реальное новое свидетельство; исход 4 ноября пересчитывается.
2. Если 15:00 попадает в интервал прежнего прогноза, его таргет меняется с 0 на 1, увеличиваются ревизия и `label_available_at`.
3. Если начало было до времени той выдачи, оно не становится положительным исходом будущего интервала; меняются календарная история и доступные будущие признаки.
4. Сырой ответ «нет» остаётся в истории ответа, но больше не перекрывает сведения дневника. В опросе можно показать «Ответ уточнён по добавленному приступу», не требуя проходить его повторно.
5. Стрик за отправленный опрос сохраняется. Прошлые замороженные признаки и сохранённая вероятность не меняются; обучение/оценка получают новую версию метки.
6. Если ошибочную запись затем удалили, снова разрешить исход по имеющимся действующим свидетельствам. При сохранившемся и не отозванном ответе опроса «нет новых начал» и отсутствии остальных начал допустимо восстановить 0 **из этого ответа**. Без такого ответа исход неизвестен. Это отличается от восстановления нуля из молчания.

Пункт 6 требует новой модели хранения ответа: нынешняя отдельная галочка удаляется при конфликте. Сырые ответы опроса вместо физического удаления должны сохранять историю и отдельно отражать, что они перекрыты дневником. Действующее поведение старой галочки нельзя автоматически объявлять такой реализацией.

Ответ «да» без времени/записи может подтверждать наличие нового начала за календарный день, но не всегда позволяет определить его положение относительно утреннего `issued_at`. Для такого прогнозного интервала сохранить неизвестный таргет до уточнения времени. При удалении последней записи не превращать сохранившееся «да» в «нет» автоматически.

## 8. Что уточнить перед реализацией

1. Принять утренний протокол с горизонтом от отправки до конца дня либо оставить полночь. Сон последней ночи не может подставляться задним числом в полночный снимок.
2. Зафиксировать определение `attack_target` и каждого клинического счётчика; пример генератора не является словарём признаков.
3. Утвердить короткий набор вопросов, необязательность профиля/цикла и правила стрика.
4. Реализовать опрос и ревизии его ответов, новый источник разметки, правила разрешения конфликтов с дневником; затем переносить отдельную галочку.
5. Новый утренний протокол проверять отдельно от v4-полуночи. Синтетический файл пригоден для проверки чтения/форматирования, но не доказывает качество реальных вероятностей.
