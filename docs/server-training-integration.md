# Подключение сбора обучающих данных на сервере

Состояние: подготовка конфигурации. Этот документ не запускает сервер и не меняет рабочие базы. Текущий балл по правилам остаётся пользовательским прогнозом; worker только обновляет отдельный псевдонимизированный набор.

## Что требуется до запуска

1. Перенести на сервер **проверенную полную версию проекта**, включая `TrainingHistoryDetails`, новые классы снимков и `export-shared-risk-training-v3.js`. Незаписанные в Git файлы не попадут туда при `git pull`.
2. Восстановить существующую базу и аватары из проверенной копии. Проверить серверную копию и восстановление до открытия внешней регистрации. Пустой том MongoDB не заменяет перенос дневников.
3. Включить авторизацию MongoDB и отдельные роли `calm_app`, `calm_risk_export_reader`, `calm_risk_training_writer` по [инструкции миграции](../backend/scripts/README-mongo-auth-migration.md). Приложению нужен доступ только к `calm`, worker читает `calm` и пишет только в `calm_risk_training`.
4. Создать на сервере собственные `.env`, `backend/.env`, `backend/.env.training-worker` с правами `600`; использовать [образец worker](../backend/scripts/training-worker.env.example). Секреты Mac не копировать. Версия согласия — `shared-model-pilot-v2`, текущий отпечаток текста — `22a2e11943c0fc73fc7e3c75dcb9145407a6c130d7f38e86db4c7334b04fd3d2`; сверить его с обновлённым API. Версия и отпечаток в backend и worker должны совпадать; preflight сравнит их и с исходным текстом. Внешнее участие оставить закрытым до проверки сайта, HTTPS, почты и копирования данных.

## Проверка без записи в базы

В корне проекта выполнить:

```sh
sh backend/scripts/check-prod-training-readiness.sh --release
```

Команда проверяет наличие файлов, права на секреты, состав Compose, `mongod --auth`, отсутствие опубликованных портов у MongoDB/backend/frontend/worker, роли в URI и совпадение согласия. Она не печатает значения секретов. Флаг `--release` требует чистое рабочее дерево: так можно обнаружить файлы, которые не попали в серверную ревизию. Проверка не подтверждает доступность MongoDB и не заменяет пробный запуск.

## Запуск после восстановления и проверки

Для всех операций использовать одинаковые четыре Compose-файла. Последний overlay монтирует новый экспортёр и не меняет работающий локальный worker старой схемы:

```sh
docker compose -f docker-compose.yml -f docker-compose.auth.yml \
  -f docker-compose.prod.yml -f docker-compose.training-worker-v3.yml \
  up -d --wait mongo backend frontend caddy training-worker
```

Затем проверить состояние контейнеров и backend:

```sh
docker compose -f docker-compose.yml -f docker-compose.auth.yml \
  -f docker-compose.prod.yml -f docker-compose.training-worker-v3.yml ps
docker compose -f docker-compose.yml -f docker-compose.auth.yml \
  -f docker-compose.prod.yml -f docker-compose.training-worker-v3.yml \
  exec -T backend wget -qO- http://localhost:8080/api/actuator/health
```

Не выполнять `down -v`: это удалит рабочие тома. Worker пересобирает активное поколение каждые пять минут и удаляет прежние поколения; отдельные офлайн-кандидаты старого поколения тоже удаляются. Модель он не обучает и не включает.

## Сверка записи с датасетом

Агрегаты без личных данных:

```sh
docker compose -f docker-compose.yml -f docker-compose.auth.yml \
  -f docker-compose.prod.yml -f docker-compose.training-worker-v3.yml \
  exec -T training-worker /bin/sh -c \
  'mongosh --quiet "$CALM_TRAINING_SOURCE_URI" --file /scripts/inspect-shared-risk-data.js'
```

Для одного пользователя и дня передать в `exec` переменные `CALM_AUDIT_USER_ID` и `CALM_AUDIT_DATE=YYYY-MM-DD` (или `CALM_AUDIT_EMAIL` вместо ID). Этот вывод содержит подробности дневника и предназначен только администратору. Сравнивать `diary`, `observedY` и `datasetRow`; отсутствие `datasetRow` проверять по `consentCurrent` и `automaticInput`. Сводные `recordedLabeledParticipantDays` и `recordedLabeledDaysWithoutRow` считают все записанные даты, включая ещё не завершившиеся, поэтому не равны числу пригодных к экспорту дней.

Строка появляется только у участника с действующим согласием версии 2 и местоположением, когда **до начала целевого дня** сохранён снимок входов версии 3, день завершился и его исход известен. Прежнее согласие версии 1 и старые снимки версии 2 не попадают в новый набор; участнику потребуется подтвердить новые условия. Приступ даёт `y=1` во все пересекающиеся дни; отсутствие приступа требует явного подтверждения. Неотмеченный день остаётся `UNKNOWN`. Планировщик backend пытается сохранить входы на завтра после запуска и затем каждые шесть часов; пользователь не обязан открывать прогноз. Старые дни без своевременного снимка не восстанавливаются задним числом.

Если worker нездоров или `stale=true`, проверять его логи и настройки, не использовать старое поколение для обучения. После отзыва согласия проверить исчезновение строк участника в следующем поколении. Перед восстановлением старой резервной копии применить процедуру сброса согласий и обучающей базы из [инструкции экспорта](../backend/scripts/README-shared-risk-training.md).

## Граница текущей схемы

Новая строка версии 3 содержит `y`, `attackCount`, балл правил, погоду, часовой пояс, сетку местоположения с шагом около 0,1°, подробности приступов и приёмов препаратов целевого дня, а также исторические агрегаты, зафиксированные до его начала. Давление в её `features.pressureMmHg` и `features.pressureDelta24hMmHg` хранится в мм рт. ст. Подробности целевого дня находятся в `diaryOutcome` и не входят в признаки `features` или `historyDetails`. `binaryPrediction` и `predictionMatched` пока `null`, поскольку рабочая модель по-прежнему основана на правилах. Идентификаторы приступов заменены HMAC-ключами для связи с препаратами; имена пользователей, почта, точные координаты и заметки не экспортируются. Полная спецификация — в [контракте данных](training-data-contract.md).

Существующий офлайн-оценщик рассчитан на схему 2 и отклоняет поколение схемы 3. Сбор версии 3 можно включить отдельно; обучение логистической регрессии и XGBoost на нём потребует отдельной подготовки признаков и проверки качества. В действующий прогноз кандидаты не включаются автоматически.
