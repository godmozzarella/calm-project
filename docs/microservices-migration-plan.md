# Подготовка Calm к переходу на микросервисы

Этот файл фиксирует состояние проекта, результаты замеров и решения о выделении сервисов. Цель подготовки — дать Calm выдерживать больше одновременных пользователей и больше данных в дневниках. Переход можно проводить по одному сервису, когда понятна его польза и проверен способ отката.

## Текущее устройство

- React обращается к одному REST API. Spring Boot обслуживает аккаунты, дневник, опросы, прогнозы и уведомления. MongoDB хранит данные приложения.
- `training-worker` уже работает отдельно и готовит исследовательские выгрузки. Его запуск описан в [инструкции по серверу](server-training-integration.md).
- Календарь запрашивает приступы и препараты за доступный диапазон дат. При раскрытии истории диапазон расширяется. Изменение проверено сборкой и тестами фронтенда.
- Планировщики рассылок выполняются внутри бэкенда. Напоминания о карточках проверяют подписки по расписанию, отправка писем и push зависит от ответа внешних провайдеров.
- Docker Compose задаёт лимиты CPU и памяти. Фактическую ёмкость VPS под нагрузкой предстоит измерить.

## Этап 1. Замерить текущую нагрузку

- [ ] Записать доступные CPU, память и место на VPS. Отдельно посмотреть потребление бэкенда, MongoDB и `training-worker` в обычные часы и во время утренних рассылок.
- [ ] Измерить задержку API, долю ошибок и медленные запросы к MongoDB. Для рассылок измерить время от запланированной отправки до ответа провайдера. Поступление уведомления на телефон проверять отдельно.
- [ ] Прогнать на синтетических данных вход, открытие дневника и календаря, сохранение приступа, прохождение опроса и просмотр прогноза. Повторить с длинной историей и параллельными запросами. Для почты, push и внешней погоды использовать заглушки или отдельную тестовую конфигурацию.
- [ ] Записать исходные значения и согласовать целевые. Для каждого прогона указать число одновременных пользователей, объём истории, среду, p95 времени ответа и долю ошибок. p95 показывает, за какое время завершаются 95% запросов.

## Этап 2. Подготовить границы внутри бэкенда

| Область | Данные и ответственность | Когда рассматривать выделение |
| --- | --- | --- |
| Дневник и опросы | Приступы, препараты, отметки календаря, ответы и история пользователя | После замеров и оптимизации частых запросов, если появится отдельная причина для независимого выпуска или масштабирования |
| Аккаунты | Профили, сессии, подтверждение почты и доступ к API | Когда станет понятен самостоятельный сценарий использования авторизации и проверен переход старых сессий |
| Уведомления | Подписки, запланированные отправки, попытки и статусы доставки | Если рассылки систематически опаздывают из-за объёма или конкурируют с API за ресурсы |
| Прогноз | Получение и кэширование погоды, оценка риска и сохранённые прогнозы | Если запросы к погоде или вычисление прогноза требуют отдельного масштабирования |
| Подготовка данных модели | Экспорт и проверка исследовательских наборов с учётом согласия пользователя | Уже выделена в `training-worker`. Изменения оценивать по его нагрузке и времени выгрузки |

Для каждой границы описать, кто меняет данные, какие данные читает другая часть и как обрабатываются ошибки. Выделенный сервис получает данные из других частей приложения через согласованный контракт.

## Этап 3. Выделить первый сервис по результатам замеров

Уведомления — первый кандидат. Сначала измерить время обхода подписок и отправки, затем ограничить обработку подписками, для которых наступило время напоминания. Если нагрузка останется заметной, выделить обработчик отправки в отдельный процесс с собственным расписанием и пределом параллельности.

- [ ] Определить, как обработчик узнаёт о новых и завершённых приступах, пройденных опросах и изменении подписок. Перед отправкой проверять, что напоминание ещё актуально.
- [ ] Согласовать способ хранения заданий и защиты от дублей при повторе и перезапуске. Проверить временный отказ провайдера, просроченную подписку и выключение уведомлений во время обработки.
- [ ] Передавать только поля, нужные для отправки. Проверить удаление данных аккаунта и ограничения на персональные данные в логах.
- [ ] Прогнать переход на тестовых аккаунтах. Проверить, что при переключении у каждого задания один обработчик, а при откате ожидающие задания можно продолжить с учётом уже отправленных.
- [ ] Сравнить задержку API и доставку с исходными показателями. Решение о переносе следующего модуля принять по этим результатам.
