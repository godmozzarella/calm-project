# Вход в Calm по почте

## Настройки

- `CALM_PUBLIC_URL` — внешний адрес фронтенда. В production это HTTPS-адрес, на который ведёт кнопка в письме.
- Для SMTP задайте `CALM_MAIL_PROVIDER=smtp`, `CALM_SMTP_HOST`, `CALM_SMTP_PORT`, `CALM_SMTP_USER`, `CALM_SMTP_PASS` и при необходимости `CALM_MAIL_FROM`. Для Resend задайте `CALM_MAIL_PROVIDER=resend`, `CALM_RESEND_API_KEY` и `CALM_MAIL_FROM` на подтверждённом домене. Отключите отслеживание переходов для писем входа, чтобы почтовый провайдер не переписывал ссылку.
- `CALM_EMAIL_LOGIN_SECRET` — необязательный отдельный случайный ключ для хэширования кодов. Если он пуст, используется действующий `CALM_JWT_SECRET`. При смене ключа потребуется заново запросить уже отправленные коды.
- Cookie имеет флаги `HttpOnly`, `Secure` и `SameSite=Strict`. Для локальной проверки по HTTP используйте `CALM_AUTH_SECURE_COOKIE=false` и один hostname для фронтенда и API. Production-профиль включает Secure и доверяет IP из штатной цепочки Caddy → nginx → backend. Backend в этой конфигурации доступен только из сети Compose.
- Формат HTML и текст письма передаются почтовому провайдеру. В логах приложения хранится статус доставки без содержимого письма. Токен находится во фрагменте ссылки и передаётся API только в JSON запроса подтверждения.

## Переход и откат

Выпускайте фронтенд и backend вместе. Используйте существующую БД и сохраните `CALM_JWT_SECRET`. Приложение добавляет индексы при старте. Для явной миграции выполните из корня репозитория под пользователем MongoDB с правами записи и создания индексов:

```bash
CALM_EMAIL_LOGIN_MIGRATION=up mongosh "$CALM_MONGO_URI" --file backend/scripts/migrate-email-login.js
```

Команда создаёт индексы хранилища `email_login_challenges` и помечает парольные поля устаревшими. Старые BCrypt-хэши и поля кодов остаются в БД. Идентификаторы, роли и данные дневника не меняются. При первом подтверждённом входе адрес становится подтверждённым. Активный клиент обменивает старый refresh-токен на cookie при обновлении JWT. Обмен одноразовый и сохраняет идентификатор сессии.

В уже отправленных письмах с шестизначным кодом используйте ссылку для входа или запросите новый четырёхзначный код.

Для отката сначала остановите новую версию и выполните ту же команду с `CALM_EMAIL_LOGIN_MIGRATION=down`. Она удалит маркер, временные запросы входа и незавершённые запросы смены адреса, начатые новой версией. Предыдущая версия снова сможет использовать сохранённые хэши существующих пользователей. Сессии, уже обменянные на cookie, потребуют повторного входа в предыдущую версию. Для аккаунтов, созданных без пароля, понадобится восстановление пароля на старой версии. Дневники при этом остаются у тех же аккаунтов.

## Проверка вручную

1. Запросите письмо сначала на новый адрес, затем на адрес тестового существующего аккаунта. Проверьте форму «Проверьте почту», ссылку, текстовую версию и четырёхзначный код.
2. Введите неверный код, затем вставьте правильный целиком. Проверьте вход и сохранность дневника существующего аккаунта. Убедитесь, что использованные код и ссылка больше не принимаются.
3. Запросите повторное письмо через 60 секунд и проверьте, что прежняя ссылка отклоняется. Проверьте также истечение отдельного кода через 10 минут.
4. Откройте ссылку во второй вкладке. Подтвердите вход и убедитесь, что исходная вкладка открыла дневник. В другом браузере или на другом устройстве вход произойдёт в открывшем ссылку браузере. Чтобы войти в исходном браузере после использования ссылки, запросите там новое письмо.
5. В профиле запустите смену адреса, подтвердите текущую почту и затем новую. В отдельной попытке проверьте отмену по ссылке на текущей почте.
6. В инструментах браузера проверьте cookie и её срок. Активность обновляет срок до 30 дней. При проверке на отдельной тестовой БД задайте `lastActivity` тестовой сессии старше 30 дней и обновите страницу. Calm должен запросить новый вход.
