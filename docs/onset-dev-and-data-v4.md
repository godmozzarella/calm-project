# Новые начала приступов: реализованный сбор v4 и dev-запуск

2026-11-03. Реализованы первые два этапа [плана](next-day-attack-model-plan.md). Модель вероятностей, ежедневный опрос о сне/стрессе и показ процентов сюда не входят. Изменения требуют отдельной выкладки для production; на VPS эта сессия ничего не запускала.

## Отметка и исход

- Интерфейс: «Новых приступов не было». Можно отметить текущий или прошедший день при продолжающемся старом приступе.
- Новый endpoint: `POST /api/risk/outcome/no-new-attack`, тело `{date, timezone}`. Прежний `/no-attack` оставлен как совместимый маршрут к новой операции; фронтенд использует новый маршрут.
- Ответ: `status=ATTACK_STARTED|NO_ATTACK_STARTED|UNKNOWN`, независимо `headachePresent`, `dayCompleted`, `outcomeDefinition=new-attack-onset-local-day-v1`.
- Будущая дата отклоняется. Начало приступа на выбранную дату отклоняет конфликтующую галочку. Продолжение старого приступа разрешает её.
- Создание/перенос нового начала отменяет отметку только на дате начала. Редактирование окончания/симптомов не очищает весь интервал. Удаление ошибочного начала не создаёт галочку из молчания.
- В новой отметке сохраняются её смысл, время и timezone. Старые записи без новой версии остаются свидетельствами старого смысла «боли не было» и имеют отдельный источник.
- Серии в статистике и их подсказки теперь означают дни без **новых** приступов; продолжающийся приступ сам по себе серию не прерывает. Старый отчёт качества прогноза наличия боли не принимает новые галочки за доказательство отсутствия боли.

## Полночь и неизменяемые входы

`OnsetDataService` вызывается каждую минуту независимо от открытия страницы. Используется часовой пояс профиля; если он ещё не задан — явно указанный timezone последней отметки. Это позволяет сохранять историю и без выбранного погодного города.

Чтобы не подмешать сведения после начала дня, входы готовятся в последнюю минуту **до** местных 00:00. Сохраняются фактическое `capturedAt`, плановая граница `plannedIssueAt` и конец целевого календарного дня `targetEndAt`. Это явно измеренное окно 60 секунд, а не выдуманное точное время выполнения в полночь.

Если запрос погоды пересёк границу или запуск опоздал, запись получает `OUTSIDE_MIDNIGHT_CAPTURE_WINDOW` и `featureUsable=false`. В первые пять минут после полуночи можно зарегистрировать пропущенный срез, но нельзя задним числом сделать его пригодным. При неизвестном часовом поясе профильный UTC не выдаётся за достоверный местный час: ставится `TIMEZONE_UNKNOWN`, и срез непригоден для основной задачи.

Отсутствие погоды/места не уничтожает снимок истории: сохраняются `WEATHER_UNAVAILABLE`, `TARGET_FORECAST_MISSING`, `LOCATION_MISSING` или `STALE_FORECAST`. `featureUsable` проверяет временную пригодность; конкретная погодная модель отдельно требует свои известные погодные поля. Фактическая архивная погода в v4-входы не подставляется.

Снимок вставляется только один раз по ключу участник/дата. Последующие изменения дневника его не обновляют. Приступы и лекарства, фактическое время которых ещё не наступило или относится к целевому дню, не становятся историческими признаками. Значение `ongoingAtIssue=null` означает неизвестное состояние, а не подтверждённое отсутствие боли.

## Хранение и поздние исправления

В основной MongoDB используются две отдельные коллекции:

| Коллекция | Содержимое |
|---|---|
| `risk_onset_input_snapshots` | Неизменяемые входы schema 4, protocol `midnight-local-v1`, target version `new-attack-onset-local-day-v1` |
| `risk_onset_daily_labels` | Текущий таргет, независимое наличие боли, время закрытия, источник, номер и история редакций |

Местная целевая дата в новых коллекциях хранится ISO-строкой, поэтому её день не зависит от timezone Java/Mongo-клиента. Моменты времени хранятся как Instant/BSON Date.

После закрытия дня: новое начало → 1; явная галочка без нового начала → 0; отсутствие обоих → null. Галочка — полноценное пользовательское подтверждение, `labelSource=USER_NO_NEW_START_MARK`, повторного вопроса завтра нет. До конца дня `dayCompleted=false`, и метка ещё не пригодна для обучения.

Сервис пересчитывает метки после успешного изменения приступов/галочек и периодически сверяет их снова. Поэтому отложенная запись или удаление исправляет прошлый таргет с новой ревизией, даже если сам день давно завершился. Учитываются также ранее созданные метки: удаление последней записи не оставляет старый положительный исход навсегда. `finalizedAt` — логическая граница дня, `labelAvailableAt` — время фактического получения данной версии.

Собираются только данные участников с текущими согласием/отпечатком, без административной блокировки. Отзыв или блокировка удаляет новые производные входы/метки; удаление аккаунта удаляет их вместе с остальными данными. Публикация набора повторно проверяет согласия и существование аккаунтов.

Новые записи приступов и лекарств сохраняют ISO-представление локального времени (`startTimeText`, `endTimeText`, `timeText`) и `updatedAt`. CSV использует текст, а не обрезку `String(Date)`. Старые BSON-времена интерпретируются с `CALM_TIME_STORAGE_ZONE` (по умолчанию UTC для прежнего контейнерного backend); неверные строки становятся null, а не «Sun N». Перевод старой базы между JVM-timezone требует отдельной проверки, автоматической миграции реальных дневников нет.

## Экспорт

`backend/scripts/export-shared-risk-onset-v4.js` запускается через `mongosh` против исходной `calm` с теми же раздельными URI/ролями и HMAC-настройками worker. Требуется `CALM_TRAINING_REBUILD_CONFIRM=YES` и совпадение текущего согласия. URI/секреты не печатаются.

```sh
mongosh --quiet "$CALM_TRAINING_SOURCE_URI" \
  --file backend/scripts/export-shared-risk-onset-v4.js
```

В `calm_risk_training` создаются **отдельные** `onset_training_examples` и `onset_export_metadata`. Сначала проверяется полностью записанное поколение, затем оно публикуется и удаляется предыдущее. Неизвестные/неполные исходы остаются в экспорте с `trainingEligible=false`; отсутствие исхода не становится нулём. Исходные `userId` и ID приступов заменяются HMAC; примечания, точные координаты и произвольные лишние поля входов не выгружаются.

Цикл существующего worker после v3-публикации дополнительно публикует v4; overlay получил монтирование нового скрипта. Это изменение конфигурации для будущей выкладки, запуск Docker здесь не требуется и не выполнялся.

Старый v3-набор сохраняет смысл наличия боли и не использует новую onset-галочку как отрицательный исход наличия боли. Старый evaluator schema 2 не является обучением v4.

Для скачивания **после публикации v4 на сервере**:

```sh
CALM_CSV_DATASET=onset-v4 ./backend/scripts/download-calm-model-v3-csv.sh
```

Результат: `~/Downloads/calm-onset-v4-with-userid.csv` для административного просмотра. Обычный запуск без переменной по-прежнему скачивает v3. `userId` не следует включать в признаки модели.

## Запуск без Docker

Для текущей проверки используется отдельная нативная MongoDB на 27018, а не существующая база на 27017. Данные находятся в `/private/tmp/calm-onset-dev/mongo` и могут быть удалены системой при очистке временных файлов. Реальные дневники туда не переносились.

Терминал 1:

```sh
mkdir -p /private/tmp/calm-onset-dev/mongo
mongod --dbpath /private/tmp/calm-onset-dev/mongo --port 27018 \
  --bind_ip 127.0.0.1 --nounixsocket
```

Терминал 2, из `backend`:

```sh
JAVA_TOOL_OPTIONS=-Duser.timezone=UTC \
MONGO_URI=mongodb://127.0.0.1:27018/calm \
CALM_UPLOAD_DIR=/private/tmp/calm-onset-dev/avatars \
mvn spring-boot:run
```

Терминал 3, из `frontend`:

```sh
npm run dev -- --host 127.0.0.1
```

Открыть `http://localhost:5173`, backend health — `http://localhost:8080/api/actuator/health`. Не запускать вторые экземпляры на занятых портах. Настоящие SMTP/production env-файлы для этого запуска не загружались.

Для текущей dev-проверки создан отдельный синтетический аккаунт `onset-dev@example.test`, пароль `CalmOnsetDev2026!`. Это только демонстрационные данные на localhost:27018. У него продолжается старый приступ и доступна отметка об отсутствии новых начал.

## Проверка

Проверяются unit-сценарии фиксированного времени, граница суток/DST, отсутствие повторного подтверждения, поздние изменения и неизвестные исходы; настоящий Mongo round-trip immutable-входов, версий меток и локального времени; HTTP-сценарии продолжения/галочки/нового начала/удаления. Отдельные Node-тесты проверяют поколения v4, приватность, согласия, неизвестные исходы и совместимость v3.

Нативный dev-HTTP smoke также проверяет, что позднее добавление приступа меняет 0 на 1 без изменения снимка и что удаление не создаёт ложный ноль. Ночной запуск проверен управляемыми часами; ожидания реальной полуночи и отдельного визуального браузерного прогона в эту проверку не входят.
